# Тестовое задание: система партнёрских отчислений

[English](README.md) | **Русский**

Пользователи образуют партнёрское дерево. С прибыли пользователя партнёры над ним (до 10 уровней) получают комиссии по
линейной схеме или схеме Фибоначчи, а начисленное периодически выплачивается им на кошельки. Я реализовал это как пять
микросервисов за API Gateway.

**Стек:** .NET 10 (ASP.NET Core Web API на контроллерах, gRPC, EF Core), PostgreSQL 17, Apache Kafka 4.1 (KRaft), YARP,
FluentValidation, Scalar, Polly, OpenTelemetry, Aspire Dashboard, Docker Compose, xUnit v3.

## 1. Запуск

### 1.1. Требования

Для запуска нужен Docker с плагинами `compose` v2 и `buildx` и примерно 4 ГБ свободной памяти. Всё собирается внутри
Docker, поэтому .NET SDK ставить не нужно.

### 1.2. Запуск системы

```bash
docker compose up -d --build
docker compose ps
```

Первый запуск занимает 1–2 минуты. Когда все .NET-сервисы перейдут в состояние `healthy`, можно работать. Схемы баз
данных создают миграции EF Core при старте сервисов, а топики Kafka создаёт одноразовый контейнер `kafka-init`.

| Компонент | Адрес |
|---|---|
| API Gateway и документация API (Scalar) | http://localhost:8080 |
| Aspire Dashboard (трассы, метрики, логи) | http://localhost:18888 |
| Kafka UI | http://localhost:8088 |
| pgAdmin (`admin@valetaxtest.dev` / `admin`, сервер уже добавлен) | http://localhost:5050 |
| PostgreSQL (`postgres` / `postgres`) | `localhost:5432` |
| Kafka для внешних клиентов | `localhost:29092` |

Порты можно поменять переменными окружения `GATEWAY_PORT`, `DASHBOARD_PORT`, `KAFKA_UI_PORT`, `PGADMIN_PORT`,
`POSTGRES_PORT` и `KAFKA_EXTERNAL_PORT`, а период выплат переменной `PAYOUT_INTERVAL` (по умолчанию `00:00:30`).

| Действие | Команда |
|---|---|
| Остановка | `docker compose down` |
| Остановка с удалением данных | `docker compose down -v` |
| Запуск нескольких экземпляров сервиса | `docker compose up -d --scale commissions=3 --scale partners=2` |
| Unit-тесты (нужен .NET SDK 10) | `dotnet test` |

### 1.3. Демонстрационный сценарий

Для быстрой проверки я написал скрипт `scripts/demo.sh` (нужны bash и curl). Он проходит сквозной сценарий через шлюз
и печатает рядом с ответами API ожидаемые значения.

Скрипт строит цепочку `root ← a ← b ← c ← d` и регистрирует прибыль `d` в размере 1000. По линейной схеме c, b, a и
root получают 10, 20, 30 и 40, по схеме Фибоначчи 10, 10, 20 и 30. После выплаты их балансы равны 20, 30, 50 и 70.
В конце скрипт блокирует кошелёк `a` и показывает, как сага выплат откатывает выплату.

## 2. Архитектура

### 2.1. Сервисы

Я разделил систему на пять сервисов. У каждого своя база данных, а к данным других сервисов он обращается только через
их API или сообщения. В docker-compose все базы лежат на одном сервере PostgreSQL под разными учётными записями.

| Сервис | Назначение | Данные |
|---|---|---|
| **Partners** | Пользователи, партнёрские связи, контроль циклов, ветки дерева | `users` |
| **Events** | Приём событий прибыли, список и детали событий | `profit_events`, копии комиссий и выплат |
| **Commissions** | Расчёт комиссий, журнал начислений, схема начисления, резерв комиссий для выплаты | `commissions`, `processed_events`, `commission_settings`, `schema_changes`, `payout_reservations` |
| **Wallets** | Кошельки, зачисление выплат, история выплат, блокировка кошелька | `wallets`, `wallet_payouts`, `wallet_payout_items` |
| **Payouts** | Запуск выплат по расписанию, оркестрация саги, таймауты шагов | `payout_sagas` |
| **Gateway** | Единая точка входа на YARP, общая страница Scalar | — |

Приём событий я отделил от расчёта комиссий. Events сохраняет событие и сразу отвечает `202 Accepted`, а расчёт,
которому нужна цепочка партнёров, идёт асинхронно и масштабируется отдельно. Если Partners или Commissions недоступны,
события ждут в Kafka.

Начисления и балансы тоже живут в разных сервисах. Выплата меняет данные и в Commissions, и в Wallets, поэтому я сделал
её сагой, которой управляет отдельный сервис Payouts. Участники саги друг о друге не знают.

### 2.2. Устройство сервисов

**Partners** хранит у пользователя только прямого партнёра, а ветки дерева читает рекурсивными CTE.

**Events** сохраняет событие и сообщение для Commissions в одной транзакции ([раздел 4.2](#42-transactional-outbox)).
Регистрацию владельца события он проверяет в Partners и кеширует положительные ответы в памяти реплики на 5 минут.
Детали события Events отдаёт из своей read-модели, где лежат копии комиссий и выплат из событий Commissions, так что
чтение не зависит от доступности Commissions.

**Commissions** считает комиссии по схемам, которые я сделал по паттерну Strategy. `LinearCommissionSchema` и
`FibonacciCommissionSchema` реализуют `ICommissionSchema`, а `CommissionSchemaResolver` выбирает нужную по типу из
`commission_settings`.
`CommissionCalculator` работает только с интерфейсом, поэтому новая схема добавляется отдельным классом без правок
расчёта. В саге выплат Commissions резервирует комиссии, подтверждает их оплату или возвращает в статус «начислена».

**Wallets** хранит баланс в колонке и меняет его в одной транзакции с записью о выплате. Результат зачисления
сохраняется по `payout_id`, поэтому повторная команда получает тот же ответ.

**Payouts** управляет сагой выплат. Состояния и переходы описаны конечным автоматом `PayoutSagaStateMachine`, а запуск
по расписанию и повтор команд без ответа выполняют фоновые задачи ([раздел 3](#3-сага-выплат)).

### 2.3. Взаимодействие сервисов

| Канал | Назначение | Свойства |
|---|---|---|
| REST/JSON через YARP | Внешний API | OpenAPI, единая страница документации |
| gRPC | Синхронное чтение данных другого сервиса | Контракт `.proto`, дедлайны, балансировка по репликам |
| Kafka | Передача изменений между сервисами (события и команды саги) | Независимость от доступности получателя, порядок по ключу, повторная доставка |

gRPC я использую только для чтения данных, которые должны быть актуальны в момент вызова.

Основные потоки через Kafka:
1. **Регистрация пользователя.** Partners публикует `partners.user-registered`, Wallets открывает кошелёк.
2. **Событие прибыли.** Events публикует `events.profit-event-registered`, Commissions считает комиссии и публикует
   `commissions.commissions-calculated`, Events сохраняет результат в read-модель.
3. **Выплата.** Payouts обменивается командами и ответами с Commissions и Wallets ([раздел 3](#3-сага-выплат)). После
   выплаты Commissions публикует `commissions.commissions-paid`, и Events отмечает комиссии выплаченными.

Регистрацию пользователя и расчёт комиссий я сделал хореографией, так как им не нужны компенсации. Для выплаты выбрал
оркестрацию.

### 2.4. Структура сервиса

Каждый сервис состоит из четырёх проектов по DDD и Clean Architecture. Зависимости направлены внутрь (`API` →
`Infrastructure` → `Application` → `Domain` → `Core`), и за этим следит компилятор через ссылки между проектами.

| Проект | Содержимое |
|---|---|
| `API` | `Program.cs` с регистрацией зависимостей, контроллеры, gRPC-сервер и `.proto`, маппинг DTO в gRPC |
| `Infrastructure` | EF Core, миграции, репозитории, запросы на чтение, gRPC-адаптеры, фоновые задачи |
| `Application` | Сервисы приложения, валидаторы, обработчики сообщений, контракты сообщений, порты, мапперы |
| `Domain` | Сущности и доменные сервисы |
| `Core` (общая библиотека) | `Money`, `ExternalIds`, `DomainException`, исключения Application, порты хранилища |

**Доменная модель.** Я использую anemic model. Сущности содержат только данные, а бизнес-правила живут в доменных
сервисах без зависимостей от инфраструктуры.

**Сервисы приложения.** На каждую область приходится один сервис приложения (`IUserService`, `IEventService`,
`ICommissionService`, `IWalletService`, `IPayoutService`), и каждой операции API соответствует один метод. Сообщения
Kafka обрабатывают классы `IMessageHandler<T>`, для сообщений они играют ту же роль, что контроллеры для HTTP.

**Валидация.** Запросы описаны парами `<Операция>Request` и `<Операция>RequestValidator` на FluentValidation. Сервис
приложения вызывает `ValidateAndThrowAsync`, поэтому правила одинаково работают для REST и gRPC. Ошибка валидации
возвращается как `400`, в gRPC как `InvalidArgument`.

**Порты и адаптеры.** Слой Application ничего не знает про EF Core, gRPC и Kafka. Он объявляет порты, а их реализации
лежат в Infrastructure. Запись идёт через репозитории и `IUnitOfWork` одной транзакцией вместе с `IOutbox`. Для чтения
есть отдельные `I*Reader`, которые загружают сущности без отслеживания изменений и превращают их в DTO. Другие сервисы
спрятаны за портами `IPartnerHierarchy`, `IUserDirectory` и `ICommissionsLedger`, их реализуют gRPC-адаптеры.

**Маппинг.** Преобразования между моделями я сделал extension-методами в папке `Mappings` того слоя, которому доступны
обе модели. Имя файла отражает направление преобразования.

**Контракты сообщений.** Каждый сервис сам объявляет сообщения, которые публикует или получает
(`Application/LinkEvents`, сообщения саги, `Topics.cs`). Сообщения передаются в JSON, имя типа идёт в заголовке
`message-type`. Файл `.proto` лежит в проекте сервера, а клиенты подключают его ссылкой.

**Общие библиотеки.** В `src/Libraries` я вынес только инфраструктурный код:
- `EventBus` — абстракции обмена сообщениями;
- `MessageLogEF` — таблицы outbox и inbox;
- `EventBusKafka` — producer, relay и потребители Kafka;
- `PersistencePostgres` — DbContext, Unit of Work, advisory-блокировки, миграции;
- `ValetaxTest.ServiceDefaults` — логирование, OpenTelemetry, health checks, обработка ошибок, gRPC-клиенты с Polly.

### 2.5. Хранение данных

| База | Таблицы и ограничения |
|---|---|
| `partners` | `users(external_id PK, partner_id FK → users)`, индекс по `partner_id` |
| `events` | `profit_events(external_id PK)`, `event_commissions`, `commission_payments` |
| `commissions` | `commissions` с уникальным индексом `(event_id, level)` и частичным индексом `(partner_id, accrued_at) WHERE status = 'Accrued'`, `processed_events(event_id PK)`, `commission_settings` (одна строка), `schema_changes`, `payout_reservations(payout_id PK)` |
| `wallets` | `wallets(user_id PK, CHECK balance ≥ 0)`, `wallet_payouts(payout_id PK)`, `wallet_payout_items(commission_id PK)` |
| `payouts` | `payout_sagas` с частичным уникальным индексом «одна активная выплата на партнёра» и индексом по `next_attempt_at` активных саг |

Во всех сервисах есть таблица `outbox_messages`, у потребителей ещё `inbox_messages`. Деньги я храню в `numeric(24,8)`.

## 3. Сага выплат

Выплата — единственная распределённая транзакция в системе. Нужно отметить комиссии выплаченными в Commissions и
зачислить сумму на кошелёк в Wallets так, чтобы ничего не заплатить дважды, а если кошелёк откажет, вернуть комиссии в
статус «начислена».

### 3.1. Выбор оркестрации

Я выбрал оркестрацию, потому что шаги саги неравнозначны. Резерв можно откатить, зачисление является точкой невозврата,
а подтверждение должно выполниться в любом случае. Такую логику проще описать одним конечным автоматом
`PayoutSagaStateMachine`, чем цепочкой подписок в трёх сервисах.

Состояние каждой выплаты хранится явно в строке `payout_sagas` вместе с текущим шагом, числом повторов и историей
переходов (`GET /api/payouts/{id}`). Таймауты и повторы обрабатываются в одном месте, участники саги друг о друге не
знают, а новый шаг добавляется только в Payouts.

### 3.2. Таймауты

Если ответ не пришёл за `StepTimeout` (30 секунд), монитор таймаутов отправляет команду текущего шага повторно. Пауза
каждый раз удваивается, но не превышает 5 минут.

По таймауту я сагу не компенсирую. После команды зачисления её результат неизвестен, и откат с последующей новой
выплатой мог бы заплатить дважды. Компенсация запускается только при явном отказе кошелька.

### 3.3. Порядок обработки

Команды и ответы идут с ключом `payoutId`, команды кошельку с ключом `userId`, так что сообщения одной выплаты
обрабатываются по порядку. Пока применяется ответ, строка саги заблокирована. Переход выполняется только из состояния,
которое ожидает этот ответ, поэтому дубли и поздние ответы игнорируются.

## 4. Надёжность

### 4.1. Идемпотентность

Kafka доставляет сообщения «хотя бы один раз», а клиент может повторить запрос, поэтому защиту от повторной обработки я
сделал на каждом уровне.

| Уровень | Механизм |
|---|---|
| Приём события | Первичный ключ `profit_events.external_id`. Повторный запрос получает сохранённое событие, гонку одинаковых запросов разрешает тот же ключ |
| Доставка сообщения | Inbox. Запись `(message_id, consumer)` вставляется с `ON CONFLICT DO NOTHING` в одной транзакции с изменениями обработчика, повторное сообщение пропускается |
| Начисление | `processed_events(event_id PK)` гарантирует однократное начисление, даже если событие пришло в другом сообщении. Дополнительно действует уникальный индекс `commissions(event_id, level)` |
| Резерв | Одна активная сага на партнёра. `SKIP LOCKED` не даёт двум резервам взять одну комиссию. Повторная команда получает снимок резерва по `payout_id` |
| Зачисление | Результат хранится по `payout_id`. `wallet_payout_items(commission_id PK)` исключает повторное зачисление комиссии |
| Переходы саги | Ответ применяется только в ожидаемом состоянии |

### 4.2. Transactional outbox

Сервисы не пишут в Kafka напрямую. Сообщение сохраняется в `outbox_messages` в той же транзакции, что и данные, а
фоновая задача `OutboxRelay` в каждой реплике отправляет его дальше:
1. берёт до 100 записей с `FOR UPDATE SKIP LOCKED`, чтобы реплики не мешали друг другу;
2. отправляет пачку идемпотентным producer'ом с `acks=all`;
3. удаляет отправленные записи.

При ошибке relay делает паузу и удваивает её до 30 секунд. Если процесс упадёт между отправкой и удалением, сообщение
уйдёт ещё раз, и его отсечёт inbox получателя. Вместе с сообщением сохраняется контекст трассировки, поэтому асинхронная
обработка видна одной трассой.

### 4.3. Обработка сообщений

Сообщения обрабатывает `KafkaConsumerService`. Обработчик выполняется в одной транзакции с записью в inbox, а offset
фиксируется только после успешной обработки или переноса сообщения в DLT.

| Ситуация | Поведение |
|---|---|
| Временная ошибка (недоступна БД, брокер или другой сервис, открыт circuit breaker) | Три попытки в процессе, затем `Seek` на то же сообщение и повтор с паузой от 1 до 30 секунд. Сообщение не теряется, партиция не продвигается |
| Постоянная ошибка (неизвестный тип, некорректный JSON, ошибка после трёх попыток) | Перенос в dead letter topic `<topic>.dlt`. В заголовках сохраняются причина, текст ошибки, исходные topic, partition и offset |

Записи inbox хранятся 8 дней, это дольше, чем Kafka хранит сообщения (по умолчанию 7 дней). Раз в час фоновая задача
удаляет старые записи.

Факт выплаты может прийти в Events раньше факта начисления, поэтому выплаты я храню отдельно в `commission_payments` и
соединяю с комиссиями при чтении.

### 4.4. Синхронные вызовы

Каждый gRPC-вызов проходит через конвейер Polly:
1. Общий таймаут 10 с.
2. Retry с тремя попытками, экспоненциальной паузой и jitter, только для временных ошибок.
3. Circuit breaker, который размыкается на 15 с при 50 % ошибок не менее чем на 5 вызовах за 30 с.
4. Таймаут одной попытки 3 с.

Если Partners недоступен, Events принимает события пользователей из кеша, а остальным отвечает `503` с заголовком
`Retry-After`. Расчёт комиссий в это время стоит и сам продолжится, когда Partners вернётся.

### 4.5. Корректное завершение

По SIGTERM сервис:
- переводит readiness-проверку в `Unhealthy`;
- даёт Kestrel дообработать текущие запросы;
- даёт потребителям Kafka закончить текущее сообщение, зафиксировать offset и выйти из группы, после чего их партиции
  сразу переходят к другим репликам;
- дожидается, пока relay отправит текущую пачку, и вызывает `Flush` у producer'а;
- откатывает незавершённые транзакции фоновых задач Payouts.

Время на завершение задаёт `Service:ShutdownTimeout` (30 с), в docker-compose `stop_grace_period` равен 40 с.

### 4.6. Логи, метрики, трассировки

Трассы, метрики и логи уходят по OTLP в Aspire Dashboard. Одна трасса проходит весь путь через шлюз, сервис, SQL, Kafka,
потребителя и gRPC. Логи дополнительно пишутся в stdout в JSON с `TraceId`, а при обработке сообщений ещё с `MessageId`
и `CorrelationId` (id события или выплаты).

Свои метрики с префиксом `valetaxtest.*` я добавил для приёма и обработки событий, начислений по схемам, саг выплат и
повторов их шагов, зачислений, публикации и обработки сообщений и DLT. Кроме них собираются метрики ASP.NET Core,
HttpClient, runtime, Npgsql и Polly.

| Проверка | Состав | Назначение |
|---|---|---|
| `/health/live` | Работа процесса | Liveness без внешних зависимостей, сбой общей БД не вызывает перезапуск контейнеров |
| `/health/ready` | БД, Kafka, отсутствие остановки сервиса | Healthcheck в docker-compose |

## 5. Масштабирование и развитие

Сервисы не держат состояние в памяти (кроме небольшого кеша в Events), поэтому любой из них можно поднять в нескольких
экземплярах через `docker compose up -d --scale <сервис>=N`. Главное ограничение — Kafka, PostgreSQL и Aspire Dashboard
запущены в одном экземпляре. Ещё я бы разнёс каждый сервис и API Gateway по отдельным репозиториям.

## 6. Справочник

### 6.1. REST API

Полное описание API есть в Scalar на шлюзе (`http://localhost:8080/scalar`), по документу на каждый сервис. Ошибки
возвращаются в формате RFC 7807.

| Код | Значение |
|---|---|
| `400` | Ошибка валидации, поля перечислены в `errors` |
| `404` | Ресурс не найден |
| `409` | Конфликт |
| `422` | Нарушено бизнес-правило |
| `503` | Недоступна зависимость, ответ содержит заголовок `Retry-After` |

Списки возвращают JSON-массив и принимают `page` (с 1) и `pageSize` (от 1 до 100, по умолчанию 20). Значение вне
диапазона даёт `400`.

### 6.2. Конфигурация

Настройки лежат в `appsettings.json` каждого сервиса, в docker-compose я переопределяю их переменными окружения
(например, `Payouts__Interval`). По умолчанию адреса БД, Kafka, gRPC и OTLP указывают на `localhost`, чтобы сервис
можно было запустить через `dotnet run`. Настройки проверяются при старте.

| Ключ | По умолчанию | Сервис |
|---|---|---|
| `Commissions:MaxLevels` | `10` | commissions |
| `PartnerTree:MaxDepth`, `PartnerTree:MaxDownlineSize` | `10`, `1000` | partners |
| `Payouts:Interval` | `00:01:00` (в compose `00:00:30`) | payouts |
| `Payouts:StepTimeout`, `Payouts:MaxRetryDelay`, `Payouts:TimeoutCheckInterval` | `30s`, `5m`, `10s` | payouts |
| `Payouts:MaxItemsPerPayout`, `Payouts:MaxPartnersPerRun`, `Payouts:SchedulerEnabled` | `500`, `1000`, `true` | payouts |
| `Outbox:PollingInterval`, `Outbox:BatchSize`, `Outbox:BatchTimeout` | `200ms`, `100`, `15s` | все, кроме шлюза |
| `Service:ShutdownTimeout` | `00:00:30` | все |
